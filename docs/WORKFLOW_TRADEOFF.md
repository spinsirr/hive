# Workflow tradeoff for Hive

Evaluated 2026-09-08 against current Hive code and official documentation. This is a retrospective assessment of an alternative available now, not evidence that Workflow was evaluated or deliberately rejected during the original build. No Workflow integration or failure experiment was performed.

**Decision after this review:** Workflow integration was deferred to keep focus on the existing [shared-task scope](ROADMAP.md#execution-architecture). The adoption guidance below describes a possible future change, not an implemented migration.

## Conclusion

Workflow is a strong candidate for Hive's execution lifecycle. It can support interactive coding agents and adds durable dispatch, persisted execution checkpoints, retries, waiting, and observability that Hive's current Postgres state does not provide. Postgres would remain useful for team membership, authored discussion, ordered input, and the shared product record. The decision is whether to add a durable executor around that domain model, not whether a database and a workflow engine are equivalent. [Workflow overview](https://vercel.com/docs/workflows), [Harness Workflow utilities](https://ai-sdk.dev/docs/ai-sdk-harnesses/workflow-utilities).

Keeping the existing path is defensible for the bounded demonstration while its limitations are disclosed. Before promising unattended recovery from process failures, I would prioritize a checkpoint-aware Workflow integration and verify its failure behavior. Simply marking the current entire coding turn as a retryable step would not be enough.

## What the current implementation establishes

- `applyTaskSessionAction()` locks the task row, applies the reducer, saves the running state and live-reply identity, then commits. The route subsequently awaits the conversation or coding runner in the original POST. That route has `maxDuration = 300`. There is a commit-to-execution gap; the transaction grants admission, not durable execution. [Task store](../src/lib/task-session-store.ts), [route](../src/app/api/sessions/[sessionId]/route.ts).
- Public output is checkpointed, and the coding runner collects artifacts plus native resume state and a Sandbox snapshot on normal completion or a caught error. Hard process termination can bypass those handlers. `isHiveRunActive()` checks stage/start/completion fields; it does not check an execution lease. The inspected execution path has no durable dispatcher or automatic stale-run recovery. A stranded running state is therefore a **static-code risk**, not a production failure reproduced by this research. The separate workspace-restore lease does not establish agent-run recovery. [Runner](../src/lib/hive-runner.ts), [active-run predicate](../src/lib/task-session.ts).

## What Workflow would add

| Concern | Concrete gain | Boundary Hive still owns |
| --- | --- | --- |
| Execution recovery | Completed step results are recorded and replayed; failed work can be scheduled again rather than depending on the original request staying alive. | Defining safe step boundaries and reconciling a partially executed external operation. |
| Interactive input | Reusable hooks accept multiple events over time; workflows can suspend until input or approval arrives. | Membership authorization, who authored a steer, queue ordering, and when Apply is allowed. |
| Output delivery | Persisted streams can be reattached from an index independently of the producer. | Task-to-run mapping, authorized readers, sanitized public output, and how stream output becomes the canonical shared transcript. |
| Operations | Run/step history, retries, and deployment-pinned execution provide an inspectable lifecycle. | A recovery policy for failed runs, old deployments, and the product state shown to teammates. |

These gains follow from the official [steps](https://useworkflow.dev/docs/foundations/workflows-and-steps), [hooks](https://useworkflow.dev/docs/foundations/hooks), [streaming](https://useworkflow.dev/docs/foundations/streaming), and [versioning](https://useworkflow.dev/docs/foundations/versioning) documentation. The right-hand column is the application-design implication for Hive.

Workflow is not limited to static or batch tasks. Its hooks implement `AsyncIterable` for repeated external events, and `WorkflowAgent` supports tool approvals surviving suspension plus resumable chat transport. This establishes interactive-agent support; it does not require replacing Hive's Codex harness with a new model-and-tools loop. [Hooks](https://useworkflow.dev/docs/foundations/hooks), [WorkflowAgent](https://ai-sdk.dev/v7/docs/agents/workflow-agent).

## The direct path for Codex Harness + Sandbox

Current official AI SDK documentation provides `@ai-sdk/workflow-harness`: `runHarnessAgentStep()` checkpoints at semantic agent-step boundaries; `runHarnessAgentTimeSlice()` checkpoints at wall-clock slices. Their returned `HarnessWorkflowState`, including `continueFrom`, is persisted within a Workflow run. These helpers materially reduce the integration work compared with inventing continuation machinery. Hive customizes the Codex bootstrap/driver, so compatibility with its installed versions, bridge continuation, and caller-owned Sandbox needs testing; this is not a demonstrated plug-and-play change. [Harness Workflow utilities](https://ai-sdk.dev/docs/ai-sdk-harnesses/workflow-utilities), [Hive adapter](../src/lib/codex-harness.ts).

Workflow orchestration code executes in a restricted deterministic context; Node.js, database, and Sandbox operations belong in steps. The utility guide specifically keeps the agent in a separate module and imports it inside the step. An individual step is still subject to Function runtime limits: a long overall workflow does not make one blocking coding invocation unlimited. Slice duration needs headroom for suspension and checkpoint writes. [Steps](https://useworkflow.dev/docs/foundations/workflows-and-steps), [runtime limits](https://vercel.com/docs/workflows/pricing).

Workflow persists serializable execution data, not an arbitrary live process or filesystem. The harness owns native conversation history; replaying the public transcript does not reconstruct it. The integration guide explicitly requires durable `resumeFrom` storage by `sessionId` across separate user-turn workflow runs. Hive must preserve valid native-session and workspace recovery data together, retain its deliberate restore semantics, and distinguish resuming an unfinished turn from submitting a new user prompt. Workflow does not automatically give Hive correct historical workspace restoration. [Harness lifecycle and history](https://ai-sdk.dev/docs/ai-sdk-harnesses/harness-agent), [serialization](https://useworkflow.dev/docs/foundations/serialization), [resume persistence](https://ai-sdk.dev/docs/ai-sdk-harnesses/workflow-utilities#resume-persistence).

## The integration costs that matter

1. **Retries need effect-level reasoning.** A step may execute again after a crash or lost success response. Stable step IDs support idempotency, but the downstream effect must honor that identity. Retrying a coding slice can otherwise repeat commands, edits, tool writes, or model work whose result was not committed. Use the harness continuation mechanism, identify attempts/checkpoints, deduplicate database updates, and define uncertain-execution recovery. Do not claim exactly-once coding turns. [Idempotency](https://useworkflow.dev/docs/foundations/idempotency), [retry controls](https://useworkflow.dev/docs/foundations/errors-and-retries).
2. **Two persistence systems need an ownership contract.** A Postgres commit and a Workflow `start()` are separate operations; adding `start()` after the current commit leaves a dispatch gap. Persist a stable execution identity and a recoverable dispatch intent, then use idempotent dispatch plus reconciliation, or another explicitly validated consistency design. The docs distinguish step idempotency from active-run coordination: hook registration and `start()` are not atomic; active hook ownership also does not deduplicate already-completed work forever. Postgres should remain authoritative for Hive's accepted commands and completed product state. This proposed design is an inference from those boundaries. [Run idempotency](https://useworkflow.dev/docs/foundations/idempotency).
3. **Hooks do not decide product authority.** A generated Workflow webhook uses its URL token as authorization. Hive should authorize the real member and task in its own route before resuming a hook, preserve the frozen steer's identity/content, and recheck the permitted state transition. Receiving an event does not decide whether discussion should become agent input. [Webhook authorization](https://useworkflow.dev/docs/api-reference/workflow/create-webhook).
4. **Streams create another recoverable view.** Workflow can remove some custom stream-reconnection work, but replacing Hive's Postgres/WS projection requires sequencing, redaction, retention, and deduplication choices. A browser disconnect and an explicit stop request have different meanings. Streaming route invocations still have time limits even though the producer can continue independently. [Workflow streams](https://useworkflow.dev/docs/foundations/streaming), [AI SDK resumable-stream cancellation](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams).
5. **Operations and cost remain explicit.** Runs stay on their starting deployment by default; fixes for in-flight work need a deliberate upgrade/recovery policy. Suspended orchestration avoids active compute while waiting, but Workflow events, data written/retained, Functions, Queues, Sandbox resources, and model usage are separate dimensions. Retention is bounded by platform policy; Workflow logs should not be assumed to be permanent team history. Retry/backoff can handle a 429 response, but cannot remove provider quotas or guarantee eventual model success. [Versioning](https://useworkflow.dev/docs/foundations/versioning), [Workflow billing and limits](https://vercel.com/docs/workflows/pricing), [Sandbox billing](https://vercel.com/docs/sandbox/pricing), [retry controls](https://useworkflow.dev/docs/foundations/errors-and-retries).

## When to adopt

Adopt when the product promise includes unattended execution after a request dies, turns that exceed a single invocation, durable waits for review/input, or operational recovery that should not depend on a teammate noticing a stuck task. These needs already expose a real gap in the current execution path. The existing Harness Workflow utilities make a small integration spike worthwhile before adding more custom liveness machinery.

Keep the present implementation for the current bounded demo if demonstrating shared steering is the immediate objective and recovery limitations are stated plainly. This saves an execution-model change before the demo; it does not establish adequate production durability.

Before switching, test: termination after database admission but before dispatch; duplicate dispatch; termination after a file/tool effect but before checkpoint commit; mid-turn continuation; a second member queuing during recovery; stale or unauthorized Apply; stream reconnection; and restoring a previous workspace while preserving current conversation and pending input. Success should mean one authorized logical turn with a reconciled outcome, not merely that a retry eventually returned.

## Summary

“Hive currently uses Postgres to coordinate the shared task and save its conversation and checkpoints. Execution still runs inside a bounded request, so a hard process failure can leave work requiring recovery. Evaluating it now, Workflow would add durable orchestration, and the AI SDK has helpers that preserve the Codex harness across step or time boundaries. I would use that before promising unattended recovery, while keeping Postgres for membership, ordered steers, and the shared task record. The remaining work is making dispatch, retries, native context, and workspace checkpoints agree.”

This wording presents a current engineering judgment and a known limit; it does not invent an original decision history or claim an integration has been built.
