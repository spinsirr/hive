# Memory tradeoff

## Eve update — reviewed 2026-09-09

Vercel's September 9 announcement adds persistent memory to **eve agents**. It is not a standalone replacement database: eve manages named slots, trusted scope resolution and the recall/capture lifecycle; the selected provider owns storage and retrieval. A provider may expose tools, capture turns automatically, or both. The built-in file provider uses private Vercel Blob on Vercel and survives restarts/deployments; its saves are model-driven tools, not automatic extraction after every turn. [Announcement](https://vercel.com/changelog/persistent-memory-for-eve-agents), [Memory overview](https://eve.dev/docs/memory)

| Boundary | Eve | Hive today |
| --- | --- | --- |
| Storage | File memory/Blob, supported hosted providers, or a custom provider. | Mem0 Cloud through Hive's server-side adapter. |
| Recall | Eve invokes provider recall before each turn. | The existing Harness `prepareCall` hook now performs one bounded host-side Mem0 search before each fresh coding turn; native continuations reuse that turn's context. Optional targeted search remains a tool. |
| Capture | Provider-specific: file-memory tools, automatic turn capture, or both. | Explicit-human-request policy; a tool selects an existing short human contribution, not an invented team summary. No automatic transcript ingestion. |
| Sharing | The example uses `byPrincipal`, but a trusted resolver can define shared tenant/workspace scope. | One GitHub installation + repository across tasks; not global memory or a personal profile. |

Eve can express shared memory too; personal-vs-team scope is a product choice, not a unique Mem0 capability. Its documentation also treats recalled memories as untrusted context, not system instructions, and distinguishes cross-session memory from session working state. These boundaries agree with Hive's separation of attributed repository conventions, durable team conversation, and native Codex recovery. [Eve scope](https://eve.dev/docs/memory#scope), [memory guidance](https://eve.dev/docs/memory#tell-the-model-how-to-use-memory), [memory versus session state](https://eve.dev/docs/memory#memory-and-session-state), [Hive collaboration skill](../src/lib/codex-bridge/hive-collaboration/SKILL.md)

**Assessment, not an implementation instruction:** Mem0 is a reasonable provider for the existing Codex/Hive runtime; the announcement does not require changing it. Eve's useful comparison is explicit lifecycle ownership: when to recall, what may be remembered, and who shares it. The narrow next acceptance remains one explicitly authorized save and recall from another task on the same repository. No Eve integration, configuration change, provider switch or model run was performed for this review.

### Does the current agent harness support memory?

Yes. Hive constructs `HarnessAgent` with its Codex adapter. The installed `@ai-sdk/harness@1.0.98` exposes async `prepareCall` for fresh prompt turns; its continuation path reuses frozen turn settings without invoking that hook again. Hive now uses it for automatic Mem0 recall. The adapter's supported `mcpServers` option separately connects the run-scoped `search_memory` and `remember_memory` tools. These APIs do not expose eve's `defineMemory` slot configuration; the eve default harness is a separate agent loop. Automatic recall therefore does not require replacing Codex, importing eve's slot API, or migrating native history. [Hive recall hook](../src/lib/hive-memory-recall.ts), [Hive runner](../src/lib/hive-runner.ts), [Codex adapter](../src/lib/codex-harness.ts), [memory tools](../src/lib/hive-mcp.ts), [Eve default harness](https://eve.dev/docs/concepts/default-harness)

### Implemented after the comparison — automatic reads, deliberate writes

- The host derives the query from the selected request/reply, not the expanded prompt or a newer queued message. A whole-thread steer uses the task title, not a synthesized claim of consensus. Unsafe or oversized queries are skipped rather than uploading or silently truncating a transcript.
- Recall reuses the existing installation/repository-scoped adapter, with at most three results, a two-second hard deadline and no retries. No additional database reads, idle timers, model summarizer, dependency or background job was introduced. The deadline aborts the request and also releases the turn if an external request fails to honor cancellation.
- Bounded text and author/session/message/reply IDs enter the user prompt as untrusted historical data, never dynamic system instructions. The actual current task remains intact and last. Native Codex history stays native; this is context enrichment, not replacing history or proving all saved conventions are current.
- Keep the base `instructions` unchanged too: the installed Codex adapter fingerprints instructions/tools and requests a fresh native thread when that fingerprint changes. An added static memory sentence was caught during post-deploy compatibility review and removed; the runner regression pins the pre-recall instruction contract. The bundled skill and per-turn context carry the memory guidance without changing that native configuration.
- Saving remains explicit via the existing tool. The production tool-signing gap did not block host-side automatic recall. It was resolved in the later owner-approved configuration update below, separately from implementing this hook; cloud acceptance is recorded separately below.
- Verification uses the real installed HarnessAgent lifecycle, real Mem0 adapter, selected-run input and runner, with controlled external boundaries. New turns, multiple tool steps, suspended/resumed continuations, scope/attribution, unsafe input, errors and a hanging request are covered. Live Mem0 save/recall and actual model adherence remain separate acceptance checks; no cloud data was written for these tests.

## Mem0 and Hive — verified 2026-09-09

Hive uses Mem0 Cloud as a repository-shared store for selected team conventions. The narrow write policy belongs to Hive; Mem0 also supports extracting reusable facts from conversations automatically. Mem0's documented model is an external memory layer: an application sends messages to `add`, retrieves relevant memories with `search`, and chooses what to include in the next model request. The architectural implication is that this supplies recalled context; native agent conversation/session continuation remains an application concern. [Mem0 architecture](https://docs.mem0.ai/core-concepts/how-it-works)

| Concern | Current Mem0 capability | Hive's implementation |
| --- | --- | --- |
| Exact writes | `infer: false` stores submitted plain-text messages without the extraction LLM. The current direct-import documentation describes synchronous `SUCCEEDED` responses with `results`; both user and assistant messages can be stored, while system messages are dropped. | Sends one selected human message/reply as a user message with `infer: false`. Hive trims outer whitespace, limits text to 1,000 characters, rejects certain obvious secret/code patterns, and attaches source IDs and author metadata. The tool description requires an explicit human request; source selection and text restrictions are enforced in code. |
| Shared recall | V3 search requires an entity identifier inside `filters`, supports `AND`/`OR`/`NOT` and metadata filters, and combines semantic, keyword and entity matching. `top_k` is configurable. | Derives `user_id` from a hash of GitHub installation ID plus repository ID. Searches `AND(user_id, app_id="hive")`, asks for three results without reranking, then discards any result whose `metadata.hive_scope` does not match. The metadata check happens after retrieval; it is not sent as a server-side filter. Session IDs are provenance metadata, so conventions can be recalled across tasks for that same installation/repository. |
| Agent history | Mem0 can receive conversation messages, but memory retrieval and native agent session history are distinct application concerns. Mem0's separate “Memory History” API tracks changes to an individual stored memory. | The MCP surface offers explicit memory search/save tools and excludes private native history from task context. It does not automatically ingest the agent transcript or resume a native agent session through Mem0. |

Sources: [Mem0 Add Memories](https://docs.mem0.ai/api-reference/memory/add-memories), [Direct Import](https://docs.mem0.ai/platform/features/direct-import), [Search Memories](https://docs.mem0.ai/api-reference/memory/search-memories), [Memory History](https://docs.mem0.ai/api-reference/memory/history-memory); local [memory adapter](../src/lib/hive-memory.ts), [MCP tools](../src/lib/hive-mcp.ts), and [human contribution selection](../src/lib/hive-tool-context.ts#L38).

The current documentation matches Hive's fixed `/v3/memories/add/` and `/v3/memories/search/` paths, authentication header, request fields and response envelopes; no material API mismatch was found in this review. Hive accepts synchronous success and also returns a distinct pending result if Mem0 responds `PENDING`, but does not poll an event to completion. Its rule against automatic retries is a deliberate policy; the current direct-import docs say identical text in the same scope is hash-deduplicated, while semantic duplicates and mixing inference modes can still produce multiple memories. [Add API](https://docs.mem0.ai/api-reference/memory/add-memories), [Direct Import behavior](https://docs.mem0.ai/platform/features/direct-import), [local response handling](../src/lib/hive-memory.ts#L76)

Verification here is public documentation plus local source inspection. No Mem0 service request was made and no credentials were inspected. This establishes the intended implementation and documented compatibility, not whether a deployed API key is configured or live memory calls currently succeed. Hive itself reports configuration separately from service availability. [Configuration reporting](../src/lib/hive-mcp.ts#L35)
